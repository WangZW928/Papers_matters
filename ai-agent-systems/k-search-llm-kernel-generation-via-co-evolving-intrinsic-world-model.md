# K-Search: LLM Kernel Generation via Co-Evolving Intrinsic World Model

## 书目信息与问题

- **作者：** Shiyi Cao、Ziming Mao、Joseph E. Gonzalez、Ion Stoica，UC Berkeley
- **来源：** [arXiv:2602.19128v2](https://arxiv.org/abs/2602.19128v2)；[K-Search 代码](https://github.com/caoshiyi/K-Search)
- **研究问题：** 将 LLM 仅作为代码候选生成器加外部进化搜索，是否会错过需要多步、非单调变换的 kernel 优化路径？能否让模型显式规划并随搜索结果更新规划？
- **阅读范围：** 搜索状态与 world model、三阶段循环、FlashInfer 与 GPUMode 实验、作者结论。

## 方法：规划与实现分离

K-Search 将 kernel 优化写成固定 evaluator 预算下的搜索。评估器对候选程序 `x` 返回正确性、延迟和元数据；错误候选得零分，正确候选得分为 `100 × 参考延迟 / 候选延迟`，再按 workload 汇总；因此 100 才对应追平参考实现（§3.1，p.3）。

1. **Action selection：** 搜索树 frontier 保存高层优化假设，如融合 head、split-K 或改变数据驻留；LLM world model 为动作估计优先级。
2. **Local refinement：** 对选中的高层意图生成具体 CUDA kernel，在局部路径上迭代至连续 K 次无改进；实现暂时失败不立即抹掉策略假设。
3. **World-model update：** 根据编译、正确性和性能证据，在树上插入想法、更新优先级或剪枝。策略规划与程序实例化相互反馈；更新只发生在上下文中，不训练模型权重（§3.3，pp.5–6）。

这一区分有价值：低层代码一次写错不必然说明高层优化方向错误；反过来，一个能编译的候选也不说明该方向值得继续投入。

## 证据与结果

- **主实验设置：** 4 类 FlashInfer attention/MoE kernel、**152 条 traces**；H100/B200，CUDA 12.8、FlashInfer 0.5.3、PyTorch 2.8.0。三种方法均用 Gemini-3-Pro-Preview、相同初始程序及 traces，每任务 **120 次候选评估**，各跑 3 次；局部停滞阈值 K=7。图中阴影是 min–max，非置信区间（§§4.1–4.3，pp.7–8）。
- **搜索方法间差距：** 平均 final score **56.13**，对照 OpenEvolve **26.68**、ShinkaEvolve **25.37**；MoE 为 **44.1** 对 **3.09**，得分比 14.3×（§4.4，p.9）。这些是相对搜索基线的得分比；Fig. 3(c) 显示生成内核很少超过专家优化的 FlashInfer，不能将 56.13 解读为 56.13× 加速。
- **实例与策略边界：** GQA decode 的 16 个 batch=1、4 个 batch=16 workload 上，K-Search 不及搜索对照；作者将其归因于 split-K 协调开销。该解释来自实现分析，未通过单因素变换实验单独验证（§§4.4、4.6，pp.9–10）。
- **TriMul：** H100 几何平均延迟 **1030 μs**；预算 **300 次**，先 GPT-5.2、后 Gemini-3-Pro 各 150 次，K=5。因竞赛提交已关闭，这是作者使用官方 evaluator 的本地结果，对照数字来自榜单；不等于官方录入成绩，也不是与主实验同预算的复测（Table 3、§4.7，pp.10–11）。

## 评议、边界与迁移

- **贡献定位：** 把“优化意图是否值得探索”与“某次实现是否成功”分开表示；失败实现可触发继续修复，高层优先级也可被后续证据改写。Fig. 2 的轨迹展示了这种行为，但轨迹解释不能代替机制消融。
- **归因缺口：** 主实验未单独消融树编辑、优先级更新和局部重试，也未对齐全部 LLM token 或墙钟成本。相同 evaluator 次数支持评估预算下的整体比较，不能确认收益主要来自所谓 world model；这里的 world model 是上下文中的假设和搜索状态更新，不是经过校准的微架构预测模型。
- **泛化与剪枝：** 搜索与报告使用固定 traces，未展示另设留出 workload 的泛化结果；四类任务也不足以证明领域通用性。永久剪枝可能误删在其他组合下有效的动作，这是待检验风险，不是论文已证实的失败。
- **对 SCALE_Forge 的启示：** 分别保存动作假设、父程序、实现尝试和实测证据；为优先级更新与剪枝保留理由和恢复路径。先用预算匹配消融确认规划层有用，再增加复杂的策略树。

## Review Questions

1. 仅增加局部重试、固定动作优先级或关闭树剪枝后，性能差距还剩多少？
2. 相同 evaluator 次数下，各方法消耗多少模型 token、编译时间和 GPU 时间？
3. 已选冠军在未见 traces 上能否保持收益，误剪枝是否可通过重新开放动作纠正？

## 价值评估

**阅读价值：很高。** 与“提案—评估—状态转移—再搜索”型 Agent loop 直接相关；应在自身 workload 上验证规划机制，不宜只引用 headline speedup。
